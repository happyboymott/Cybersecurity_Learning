# 热身关-HTTP/鉴权

## 目标：
巩固鉴权失效与访问控制失效的相关知识

## 环境:
PortSwigger Web Security Academy的靶场，难度统一为APPRENTICE,全过程通过bp进行抓包

## 实验1:
Username enumeration via different responses(APPRENTICE难度)

步骤:
1.进入网站首页，找到登录功能点

![登录功能点图片](../images/屏幕截图%202026-11-11%20195433.png)

2.抓取登录数据包

![bp抓取到的登录数据包](../images/屏幕截图%202026-11-11%20195030.png)

3.将数据包发到intruder模块，选用sniper模式，并将username参数添加为待爆破参数

![intruder模块中用户名待爆破的数据包](../images/屏幕截图%202026-11-11%20195059.png)

4.将提示的用户名填入payload

![用户名payload导入](../images/屏幕截图%202026-11-11%20195107.png)

5.开始进行爆破,发现不同长度的响应信息，其中提示错误密码，猜测网站将用户名错误与密码错误的响应分离，当前用户名为正确用户名

![用户名爆破结果界面](../images/屏幕截图%202026-11-11%20195136.png)

6.根据上一步猜测，将用户名改为ec2-user，添加密码为待爆破参数，并导入提示密码字典作为payload

![intruder模块中密码待爆破的数据包](../images/屏幕截图%202026-11-11%20195203.png)

7.密码爆破成功，其中一个结果响应码为302，长度明显偏短，猜测此前的用户名结合本次爆破的密码即为正确登录信息

![密码爆破结果界面](../images/屏幕截图%202026-11-11%20195242.png)

8.将两次爆破获取的用户名与密码填入，成功登录账户，完成实验

![将正确信息填入](../images/屏幕截图%202026-11-11%20195312.png)

![成功登录后界面](../images/屏幕截图%202026-11-11%20195323.png)

结论: 
漏洞成因为针对用户名与密码错误显示不同的提示，导致攻击者有机会枚举用户名，另外没有做任何的登录错误限制，导致攻击者可以无限进行尝试,修复方向为统一外在响应特征，使用模糊化通用提示，其次实施速率限制，防止高频探测请求，同时针对一定次数的连续失败，进行人机验证或是账号锁定，最后启用多因素认证


## 实验2:
2FA simple bypass(APPRENTICE难度)

步骤:
1.进入登录功能点，填入已知凭证，准备登录

![登录功能点](../images/屏幕截图%202026-11-11%20154152.png)

2.登入后发现需要输入安全码，从电子邮件客户端获取到安全码

![安全码输入界面](../images/屏幕截图%202026-11-11%20164307.png)

![电子邮件客户端界面](../images/屏幕截图%202026-11-11%20164312.png)

3.成功登录，之后抓取目前登录的数据包保存

![登录后界面图片](../images/屏幕截图%202026-11-11%20164328.png)

![当前登录的数据包](../images/屏幕截图%202026-11-11%20164342.png)

4.根据已知信息登录目标账号carlos，bp抓取到2FA验证界面的数据包，保存cookie信息

![抓取到carlos的2FA验证数据包](../images/屏幕截图%202026-11-11%20164537.png)

5.根据此前保存的wiener用户的已登录数据包进行修改，将id参数改为carlos，cookie信息同步替换上一步为保存的carlos的cookie信息

![成功登录的bp预览界面](../images/屏幕截图%202026-11-11%20164709.png)

6.成功登录carlos账户，完成实验

![实验完成界面](../images/屏幕截图%202026-11-11%20170834.png)

结论:
漏洞成因为登录状态错误的提前下发，服务器在第一步密码验证后就下发了完整的cookie信息，导致攻击者通过第一步拿到的cookie信息直接访问用户界面获取未授权账户的控制权，修复方向为拆分会话权限状态，在用户完成第一步密码验证后下发一个权限受限的临时凭证，在完成第二步2FA之前所有核心业务与路由均拒绝临时凭证


## 实验3:
Password reset broken logic(APPRENTICE难度)

步骤:
1.进入登录界面，发现忘记密码功能点

![登录界面图片](../images/屏幕截图%202026-11-11%20165017.png)

2.将已给的账户信息填入，从邮箱获取到重置密码链接

![重置密码界面](../images/屏幕截图%202026-11-11%20155800.png)

![邮件收到重置密码链接图片](../images/屏幕截图%202026-11-11%20155809.png)

3.打开重置密码链接，填入新密码admin，提交时开启抓包，抓到重置密码的数据包后对username参数进行修改

![重置密码链接打开后界面](../images/屏幕截图%202026-11-11%20155817.png)

![修改后的重置密码数据包](../images/屏幕截图%202026-11-11%20155854.png)

4.利用修改后的密码成功登录carlos账户，完成实验

![成功登录carlos账户界面](../images/屏幕截图%202026-11-11%20155931.png)

结论:
漏洞成因为服务器后端只校验了验证码是否有效，却没有校验该验证码是否属于当前需要修改密码的目标账户，导致直接重置了他人的密码，修复方向为实现身份、凭证与会话的强绑定同时收拢用户标识的来源，服务器在生成验证码时要与当前用户ID(手机号/邮箱)与当前会话进行一对一绑定，在最后进行密码更新的操作时，后端根据验证通过的session自行映射出对应的账号，同时核对当前提交账号，凭据与会话三者是否完全一致


## 实验4:
Unprotected admin functionality(APPRENTICE难度)

步骤:
1.使用dirsearch对目标进行目录爆破，发现存在robots.txt，其中可能有关键信息

![dirsearch工具针对目标进行扫描的界面](../images/屏幕截图%202026-11-11%20180100.png)

![dirsearch工具的针对目标的扫描结果](../images/屏幕截图%202026-11-11%20181712.png)

2.访问robots.txt发现疑似后台管理界面的路径

![robots.txt的文件内容](../images/屏幕截图%202026-11-11%20160300.png)

3.访问后发现无鉴权直接登录了管理员后台

![管理员后台界面](../images/屏幕截图%202026-11-11%20160317.png)

4.删除用户carlos，完成实验

![删除用户后实验完成图片](../images/屏幕截图%202026-11-11%20160326.png)

结论:
漏洞成因为在robots.txt文件中泄露了后台管理地址，同时后台管理界面缺乏鉴权机制，导致攻击者在信息搜集后直接访问后台管理地址获取管理员权限，修复方向主要是建立全局强制的身份认证（Authentication）与细粒度权限校验（Authorization）机制，并配合网络层隔离，除此之外可以清除robots.txt内所有涉及后台管理地址（如 /admin/）、测试接口、备份文件目录、内部系统路径或未公开项目的 Disallow 规则


## 实验5:
User role controlled by request parameter(APPRENTICE难度)

步骤:
1.先根据已知信息登录上wiener账户

![登录wiener账户后界面](../images/屏幕截图%202026-11-11%20160446.png)

2.根据已知信息直接访问/admin路径，发现存在鉴权，需要管理员用户才可使用

![直接访问/admin路径后的提示界面](../images/屏幕截图%202026-11-11%20160459.png)

3.抓包发现cookie中存在admin参数，值为false,猜测其可能为鉴权的关键信息，将其值改为true后，成功访问到后台界面

![修改后的访问数据包](../images/屏幕截图%202026-11-11%20160546.png)

![后台管理界面图片](../images/屏幕截图%202026-11-11%20160554.png)

4.抓取删除操作数据包，将其中的admin参数赋值为true,成功删除用户carlos，完成实验

![修改后的删除操作数据包](../images/屏幕截图%202026-11-11%20160639.png)

![删除操作完成后界面](../images/屏幕截图%202026-11-11%20160648.png)

结论:
漏洞成因为服务器将本该由后端进行严格管控的权限状态明文放置在客户端，同时无条件信任用户提供的cookie信息，没有根据用户的登录凭据去服务器数据库或是缓存中验证用户真实身份,修复方向为将角色权限收敛到服务端存储，cookie只放置一个高熵，不可预测的随机会话标识符(Session ID)，并将此值存放到服务器的内存数据库或Session存储中，同时记录其的user_id和真实角色，每次收到敏感请求，通过Session ID到服务器查询权限，彻底删除前端cookie中的admin参数
