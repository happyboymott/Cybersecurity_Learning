# 测试清单 

## 目标:
建立一个可复现,可参考,可优化的测试清单,将渗透测试流程逐渐系统化

## 环境:
所有提到的工具基于windows系统

## 步骤:

## 信息搜集

### 域名信息收集
1. 子域名信息收集:利用工具或在线引擎等进行子域名信息搜集,逐一记录得到的子域名信息

### 人员信息收集
1. whois查询:利用在线查询或是工具针对域名的注册信息进行查询,记录域名所有者相关信息
2. 备案信息查询:利用ICP备案信息查询系统,获取并记录名称,备案编号,网站负责人,法人,电子邮箱,联系电话等信息

### 站点信息收集
1. web指纹识别:利用浏览器插件或是工具获取并记录站点指纹信息,如脚本语言,中间件,插件等信息
2. 旁站与C段信息(仅明确授权时进行):利用nmap或是在线引擎收集并记录网站的旁站和C段信息
3. 敏感目录/文件搜集:使用dirsearch等工具进行敏感目录与文件的扫描,记录收集到的信息
4. waf识别:利用wafw00f等工具或是查看拦截界面等判断网站是否启用waf以及waf的类型
5. CDN判断:利用全球ping或是访问子域名等方法判断目标是否开启CDN服务

### IP信息收集
1. 主机发现(仅明确授权时进行):使用nmap等工具进行基于目标IP网段的主机发现
2. 端口扫描:使用nmap等工具对目标IP进行端口扫描
3. 服务探测:使用nmap等工具对目标IP进行服务探测

### 错误信息收集
1. 授权环境下,针对参数进行留空或传入错误类型,不存在的资源编号等,观察响应信息
2. 检查错误响应中是否泄露框架/数据库名称,版本,服务器绝对路径,SQL片段等信息
3. 记录触发请求与关键响应

### Cookie与HTTP请求/响应
1. 查看响应头中的Server,X-powered-by等信息,以此作为版本信息线索
2. 查看Set-Cookie信息,记录Cookie的名称,HttpOnly,Secure,Samesite等信息(笔记中不保留真实会话值)
3. 对比登录前后,退出前后的Cookie变化
4. 观察Location是否暴露内部地址,敏感页面的缓存策略是否合理

## 注入

### 输入点
1. URL与常规参数:query参数,url路径参数
2. 请求体:传统表单,json的键值对,XML报文
3. HTTP请求头:UA,Authorization,Referer等
4. cookie与会话数据:Cookie中的跟踪ID,用户的偏好设置等
5. 文件上传相关:上传的文件名,文件的元数据等
6. 二次注入:注册时的邮箱/昵称等

### 漏洞发现
1. SQL注入

    1. 高危参数特征:id,uid,category,type,order,sort,keyword,username,date

    2. 测试手法:

        1. 数字型/字符型闭合测试:',",\,),')等

        2. 逻辑运算与排序位测试:1-0,1+1等

    3. 检查重点:

        1. 直接报错:页面或接口返回数据库报错堆栈

        2. 内容差异(布尔盲注):对比 AND 1=1 与 AND 1=2 时,返回的数据条数,页面长度或 HTTP 状态码(如 200 变 500 或 404)是否不同

        3. 响应时间(时间盲注):注入 SLEEP(5),pg_sleep(5) 或 WAITFOR DELAY '0:0:5' 后,观察接口响应耗时是否明显增加 5 秒。

2. 命令注入

    1. 高危参数特征:ip,host,domain,url,cmd,exec,ping,target,filename(如涉及图片压缩,PDF 转换,视频转码)

    2. 测试手法:

        1. 命令连接符: ; , | , || , & , && , 反引号 ` , $( )

        2. 配合基础无害命令:id,whoami,sleep 5,ping -c 4

    3. 检查重点:

        1. 回显特征:响应体中是否直接夹杂了系统用户(如 uid=33(www-data)),目录列表或报错信息(如 sh: 1: ... not found)

        2. 时间延迟:构造 | sleep 5 或 & timeout 5 后,请求是否精确卡顿 5 秒

        3. 带外通信:无回显时,使用 curl,wget 或 nslookup 域名 触发 DNSLog / HTTP 交互平台,查看平台是否收到来自目标服务器 IP 的解析或访问记录(有实测经验)

3. 路径遍历 / 任意文件读取

    1. 高危参数特征:file,path,filepath,dir,download,name,doc,template,lang,include,url

    2. 测试手法:

        1. 目录跳转符:../,..\,双写绕过 ....//,URL 编码 %2e%2e%2f 或双重编码

        2. 结合系统常见敏感文件路径(Linux 测 /etc/passwd,/proc/self/environ:Windows 测 C:\Windows\win.ini:Java 测 WEB-INF/web.xml)

    3. 检查重点:

        1. 文件特征内容:响应体中是否出现 root:x:0:0:,[extensions] 或应用配置文件(如 application.yml,.env)的明文源码

        2. 报错路径泄露:即使读取失败,查看报错信息(如 No such file or directory in /var/www/html/...)是否暴露了服务器的真实物理路径与操作系统类型

        3. 下载响应头:观察 Content-Disposition 响应头中的文件名变化,确认后端是否直接将参数拼接到了文件流读取函数中

4. SSRF[待专题开展之后进行补充]

## 鉴权

### 鉴权凭据
1. 会话凭证:Cookie(如 JSESSIONID,PHPSESSID),请求头中的 Authorization(Bearer <JWT>,Basic),自定义 Token 头(X-Auth-Token,Access-Token)

2. 资源归属标识:URL 路径或请求体中代表“对象身份”的字段,如 user_id,account_id,order_no,tenant_id(多租户系统),org_id,file_id

3. 权限控制参数:隐藏在表单或 JSON 中的角色与状态字段,如 role=user,is_admin=false,group_id=2,permission,step=1

### 漏洞发现
1. 未授权访问

    1. 业务场景:后台管理接口,敏感数据查询 API,文件下载接口,密码重置接口,内部监控页面(如 Swagger,Actuator)

    2. 测试手法:

        1. 剥离凭证重放:将抓到的正常业务请求中的 Cookie,Authorization 或 Token 字段直接删除或置空后重发

        2. 路径/后缀变形:尝试在受限路径后加斜杠 /admin/,加分号 /admin;test,大小写转换 /Admin 或添加 .json/.html 后缀(绕过基于路径前缀的网关拦截)

    3. 检查重点:

        1. 原本预期返回的404,403或是302跳转到登录页面,但是实际上状态码返回了200 OK

        2. 业务数据泄露:响应体中依然返回了正常的业务 JSON 数据,列表记录,或者状态码虽为 302 跳转,但响应体(Response Body)里已经完整渲染了后台页面的 HTML 代码(前端重定向导致的数据泄露)

2. 垂直越权

    1. 业务场景:普通用户访问管理员功能(如新增用户,审核订单,导出全量报表,修改系统配置,删除他人帖子)

    2. 测试手法:

        1. 接口重放:先用管理员 C 抓下所有高权限功能的数据包,然后把请求头里的凭证替换为普通用户 A 的凭证直接重发

        2. 参数篡改提权:在注册,修改个人资料或创建数据时,在请求体中手动新增或修改特权字段(如将 "role": "user" 改为 "role": "admin",或添加 "isAdmin": 1)

    3. 检查重点:

        1. 操作执行成功:普通用户发包后,未收到“权限不足”的拦截提示,而是返回了操作成功的状态码(200)及业务成功标识

        2. 权限持久化提升:篡改参数后重新登录或查询个人资料接口,发现返回的角色字段已变为管理员,或前端页面动态渲染出了原本隐藏的管理菜单

3. 水平越权 / IDOR

    1. 业务场景:同级别角色（普通用户 A）通过修改对象标识符,访问或操作另一同级用户（普通用户 B）的私有资源与数据（如查看他人个人资料/收货地址、遍历他人历史订单详情、下载他人私有附件/电子发票、修改他人账户绑定信息、取消他人订单或申请退款、读取他人私信记录、删除他人创建的草稿或评论）

    2. 测试手法:

        1. 替换对象 ID:用账号 A 登录后发起请求,将请求中的 user_id,order_id 等参数修改为账号 B 的对应 ID

        2. 跨账号替换凭证:保留账号 B 的请求数据包和目标 ID,仅把请求头中的 Token/Cookie 替换为账号 A 的凭证后重发
    3. 检查重点:

        1. 响应内容比对:观察使用 A 的凭证请求 B 的数据时,响应包的长度(Content-Length)和结构是否与 B 自己请求时完全一致,且响应体中明确出现了账号 B 的敏感信息(如 B 的手机号,邮箱,订单金额)

        2. 状态变更生效:对于修改/删除类接口,接口返回 {"code": 0, "msg": "success"} 或 true,且登录账号 B 验证时,发现数据确实被修改或删除了

4. 密码重置与验证码逻辑缺陷

    1. 业务场景:忘记密码找回,手机号快捷登录,绑定新邮箱,高危操作二次验证

    2. 测试手法:

        1. 修改接收端参数:第一步输入自己手机号获取验证码,提交验证时抓取数据包,将里面的 phone 字段修改为目标受害者手机号,保留自己的正确验证码

        2. 修改响应包绕过(前端校验):故意输入错误验证码,抓取服务端返回的响应包,将 {"success": false, "code": 400} 修改为 {"success": true, "code": 200} 后放行

        3. 跳过中间步骤:直接访问最终重置密码的接口,跳过“发送/校验验证码”的前置步骤

    3. 检查重点:

        1. 凭证与身份错位:服务端只校验了“验证码本身是否有效”,而未校验“验证码与当前提交的手机号是否绑定”,直接进入下一步或返回了目标用户的重置 Toke

        2. 响应篡改后进入下一步:修改响应包后,前端页面直接跳转到了“设置新密码”界面,且最终提交新密码时后端未再次校验前置状态,导致密码修改成功

## 业务逻辑

### 业务关键节点
1. 数量与金额参数:amount,price,total,num,count,quantity,discount,points(积分),fee(运费/手续费)
2. 流程状态标识:step,status,stage,order_state,pay_status,verified=true,is_first=1
3. 限流与次数控制:limit,daily_count,invite_code,手机号/邮箱绑定关系,活动有效期时间戳

### 漏洞发现
1. 交易支付与数值篡改

    1. 业务场景:购物车结算,生成订单,充值提现,积分商城兑换,打赏/转账

    2. 测试手法：

        1. 负数与零值测试:将商品数量 count 改为 -1(利用“买一件正价商品 + 买一件数量为 -1 的商品”抵消总价),或将支付金额 amount 改为 0,0.01,0.001(测试四舍五入精度截断)

        2. 替换商品/规格 ID:下单高价商品时,在提交订单的数据包中将 sku_id 或 price 替换为低价商品的 ID 或价格  

        3. 重复使用优惠:在同一个订单请求中传入多个相同的优惠券 ID(如 coupon_ids=[101, 101, 101]),观察是否叠加抵扣

    3. 检查重点:

        1. 订单金额异常:最终生成的订单或跳转至第三方支付(支付宝/微信/Stripe)的待支付金额变为了 0.01 元,甚至出现了订单生成后直接显示“已支付”状态

        2. 余额反向增加:转账或退款时输入负数,导致发起方的账户余额不减反增

2. 业务流程乱序与步骤跳过

    1. 业务场景:用户注册向导,实名认证,下单—支付—发货—退款闭环,密码找回,问卷/考试提交

    2. 测试手法：

        1. 跳过中间步骤:正常流程为 Step 1 (填写资料) -> Step 2 (支付/短信验证) -> Step 3 (完成开通),在完成 Step 1 后,直接抓取并重放 Step 3 的最终提交接口

        2. 状态机逆向/错位操作:订单处于“已取消”状态时重放“申请退款”接口:订单处于“已发货”状态时重放“修改收货地址”或“取消订单”接口  

    3. 检查重点:

        1. 状态非法跃迁:服务端未校验前置状态(如未检查 is_paid == true),直接执行了 Step 3 的数据库写入操作,导致未付款直接开通 VIP 或重复获得退款

3. 频率限制绕过与批量防刷缺陷

    1. 业务场景:发送短信验证码,邮件验证,图形验证码校验,邀请好友助力

    2. 测试手法：

        1. 绕过前端倒计时:忽略前端 60 秒禁用按钮,直接用 Repeater 连续重发短信请求

        2. 修改参数绕过频控:在手机号后加空格,区号(+86,0086),逗号分隔多个手机号(13800001111,13800002222),或修改 X-Forwarded-For IP 头  

        3. 验证码复用与空值测试:正确输入一次图形验证码后,重放同一请求看该图形码是否未销毁:将 captcha 参数删除或置空后发包

    3. 检查重点:

        1. 限制失效:同一手机号在 1 分钟内连续收到多条短信,或同一图形验证码可被重复使用上百次,导致接口暴露在短信轰炸或自动化撞库风险下

4. 新人专享礼包,邀请有礼,每日签到,抽奖转盘,限时秒杀

    1. 业务场景:电商大促秒杀,App拉新裂变活动,会员积分商城兑换,节日营销抽奖,每日活跃度任务

    2. 测试手法：

        1. 边界值与并发刷取:针对“每人限领一次”的活动,使用 Burp Turbo Intruder (待验证)进行毫秒级并发请求(Condition Race);或尝试修改 activity_id 遍历历史未下线的旧活动

        2. 循环自我邀请:账号 A 邀请账号 B,B 再邀请 A:或利用邮箱别名(如 test+1@gmail.com,test+2@gmail.com)批量注册小号触发同一主账号的邀请奖励 

    3. 检查重点:

        1. 资源超发:账户卡包中出现了多张新人券,积分突破每日上限,或成功领取了已过期/未开始活动的奖品

5. 拒绝服务

    1. 业务场景:分页列表查询,报表导出,图片验证码尺寸控制,文件压缩包解压上传

    2. 测试手法(下列手法仅用于自有隔离靶场,src下默认不使用)：

        1. 超大分页参数:将查询接口中的 page_size=10 修改为 page_size=9999999

        2. 图形尺寸放大:如果验证码接口支持传入宽高参数(如 /captcha?width=100&height=40),将其修改为 width=50000&height=50000

    3. 检查重点:

        1. 响应时间剧增或 502/504 报错:接口耗时从几百毫秒飙升至数十秒,甚至导致后端内存耗尽(OOM)服务短暂崩溃

6. 敏感信息过度暴露

    1. 业务场景:前端页面只展示部分脱敏数据(如隐藏了手机号中间四位,隐藏了他人邮箱),但后端接口返回了完整对象

    2. 测试手法：

        1. 正常浏览网页(如查看商品评价,查询物流状态,查看公开个人主页),在代理工具中完整审阅所有 XHR/Fetch 接口的 JSON 响应包

    3. 检查重点:

        1. 响应体冗余字段:前端页面虽然显示 138****1234,但抓包发现后端返回的 JSON 中直接包含了 "mobile": "13812345678","id_card","password_hash" 或内部审核备注等敏感字段
