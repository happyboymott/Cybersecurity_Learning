## 步骤:

### 实验1:Basic SSRF against the local server

1. 入口:商品介绍页面的查看库存功能

2. 可控参数:查询库存的数据包中的stockApi

3. 服务器请求链路:攻击者从stockApi传递恶意参数->服务器缺乏过滤->服务器调用底层网络库访问攻击者提供的地址(身份转换)->被访问地址发出响应(服务器内网等)->服务器将响应内容显示到页面(有回显)

4. 验证证据:服务器成功回显原本需要管理员权限或是本地回环地址访问的管理后台界面

5. 漏洞根因:服务器对stockApi参数的传入值缺乏过滤，同时管理后台允许本地地址无鉴权访问，导致攻击者可以写入本地地址让服务器自身发起请求，因此以可信来源访问来绕过后台鉴权限制

6. 修复方向:对于stockApi参数传入的值进行白名单过滤，同时对于本地地址的访问同样进行鉴权

7. 信任边界:
    1. 边界一（外部不可信区 ↔ Web 应用服务器）：外部用户处于完全不可信区域，stockApi 作为外部可控输入跨越此边界进入应用服务器
    2. 边界二（Web 应用服务器 ↔ 本机回环/内部管理服务）：应用服务器作为对外请求发起方（网络库起点），与本机回环接口（127.0.0.1）及内网管理后台之间存在第二道信任边界
    3. 问题:用户输入未经过充分校验就当成了请求的目标，后台将回环地址访问当做了已授权访问

### SSRF防御与过滤分类表

1. 防护方式:地址黑名单
    1. 检查对象:危险协议(file://、gopher://),畸形字符(@、\),特殊主机名(localhost,metadata.google.internal),内网/保留 IP 网段
    2. 局限:只能过滤黑名单内存在的危险输入，难以完全覆盖IP进制转化或是url解析差异等绕过手法
    3. 修复建议:采用白名单机制,正确校验解析后的真实 IP,统一 URL 解析器，禁用或严格校验 HTTP 重定向
2. 防护方式:地址白名单
    1. 检查对象:协议(http / https)，用户信息，主机名，端口，路径，特殊控制字符(\r、\n)
    2. 局限:单白名单过滤依赖于校验逻辑的实现，如果校验逻辑存在问题(如未进行全等比较)则容易被绕过，同时单白名单过滤也面临URL 解析器差异与开放重定向等问题的风险
    3. 修复建议:对于高安全场景，最佳为彻底重构参数传递方式，只接收业务id，不能重构则考虑加强验证逻辑，同时统一url解析器，禁用或严格校验 HTTP 重定向
3. 防护方法:域名解析后的IP检查
    1. 检查对象:全量解析记录,IPv4 保留网段,IPv6 保留及映射网段
    2. 局限:只解析域名后的IP，但是检验时解析出来的IP与实际连接的可能不同，其受到DNS重绑定，301 / 302 HTTP 重定向跳板，多 A/AAAA 记录轮询等问题的风险
    3. 修复建议:强制绑定校验后的 IP 发起请求，禁用自动重定向，遍历所有解析记录，同时校验 IPv4 与 IPv6
4. 防护方式:重定向处理
    1. 检查对象:Location 响应头，目标协议，状态码与请求方法，跳转计数器，跨域敏感请求头
    2. 局限:如果开发人员进行了不完全的校验，那么程序依旧面对多级跳转链绕过，协议相对 URL绕过，DNS 重绑定绕过等手法的威胁
    3. 修复建议:条件预先情况下优先彻底禁用自动重定向，必须支持重定向则构建“闭环递归校验器”，严禁使用 HTTP 客户端自带的自动跳转功能，必须手动编写一个 while 循环来接管每一次跳转，同时
 限制允许的重定向状态码与方法
5. 防护方式:网络出口限制
    1. 检查对象:目的 IP 地址,目的端口,传输层协议,发起进程/用户身份,HTTP 请求头与方法
    2. 局限:单纯依赖网络出口限制将面临无法防御“本机环回（Loopback）”流量，难以兼顾“允许访问任意公网”的业务需求，遗漏 IPv6 出站流量，DNS 基础设施侧信道泄漏等问题
    3. 修复建议:构建“主机内核级防火墙 + 专用出站代理网关 + 应用层绑定”的纵深防御体系，进行主机层加固，引入优秀隔离架构，隔离高危业务节点等
6. 补充:
    1. 地址分类
        1. 回环地址:自己指自己，数据包不会离开本机网卡，直接在操作系统内核协议栈内部完成收发，用于本机进程间通信与本地服务测试，防护时不要只拦截 127.0.0.1，警惕 0.0.0.0，警惕畸形进制与缺省写法，注意云安全组防不住回环流量
        2. 私有地址:局域网内部专用，在公网上不可路由，仅在企业内网、家庭局域网、数据中心或云 VPC 内部使用，访问公网需经过 NAT 转换，防护时注意 172.16.0.0/12 的精确边界
        3. 链路本地地址:仅在当前直连链路有效，路由器绝不转发到其他网络，用于网卡自动配置及公有云元数据服务（如 169.254.169.254），防护时注意它不属于传统私有网段极易被正则漏检（IPv4 为 169.254.0.0/16，IPv6 为 fe80::/10），警惕 IPv6 映射（如 ::ffff:169.254.169.254）与十进制/十六进制变形，云安全组可能无法拦截需依赖主机防火墙与强制开启 IMDSv2
        4. 公网地址:全球唯一且可路由，由 IANA 统一分配给全球组织和个人，可在整个公共互联网上直接寻址和通信，防护时警惕“IPv4 映射的 IPv6 地址”伪装，防范 DNS 重绑定，警惕“合法公网 IP 的 302 重定向”，避免使用“黑名单排除法”来定义公网地址

## 结论:
ssrf漏洞的主要成因为代码层面不充分的过滤，所以编写程序时的安全意识很重要

### 自检:
1. 为什么这是服务端发起的请求而不是浏览器跳转？
    1. 因为ssrf本身是利用目标站点自身设计的请求功能，其发出请求调用的是目标服务端底层的网络库，其与攻击者的客户端无关
2. 本关为什么能够访问内部功能？
    1. 因为服务器设计的时候允许本地回环地址无鉴权访问管理后台，而ssrf本身就是服务器自身发起的请求，满足无鉴权条件
3. 为什么只检查最初的url不够？
    1. 攻击者依旧可以通过开放重定向绕过的手法，先用合法域名通过校验，之后进行重定向访问内网等限制地址，另外url解析器本身因为差异问题可能导致错误通过后允许访问限制地址，同时域名解析本身的结果也可能存在非预期值
4. 为什么限制请求目的地后，内部管理功能仍需要鉴权？
    1. 因为目的地限制手法本身解决的是“防止服务器被当成内网代理/跳板”的问题，而内部管理功能鉴权解决的是“确保只有合法授权的人或服务才能执行管理操作”的问题，两者结合才能形成完成安全闭环
